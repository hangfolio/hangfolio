# S4: Reading the Pages build type with the job token

- Date: 2026-10-04
- Result: pass
- Decision: Keep the plan. The `preflight` job of `build.yml` runs `gh api repos/$REPO/pages` with `GH_TOKEN: ${{ github.token }}` and reads `.build_type`. Exit 0 gives `workflow` or `legacy`; a failure whose stderr contains `HTTP 404` means Pages is off (`none`); any other failure is its own state (`error`), never `none`. The caller keeps `pages: read` on the build job, because `actions/configure-pages` needs it too and the engine's jobs declare it.

**Question.** Can `GITHUB_TOKEN` with `pages: read`, inside a reusable workflow called from the site repo, call `GET /repos/{repo}/pages` and read `build_type` in all three states: Pages off, branch (legacy) mode and GitHub Actions mode?

**What was tried.** Three throwaway repositories in the `hangfolio` org. `hangfolio/spike-engine` holds the reusable `build.yml` and `deploy.yml` (tag `v1` = commit `09c6f0f`). Its `preflight` job declares `permissions: { pages: read }` and makes the call above. `hangfolio/spike-template` is a minimal Astro 7.3.5 site whose `.github/workflows/deploy.yml` follows SPEC 8.1: `permissions: {}` at the top, then `build` (`contents: read`, `pages: read`) calling `build.yml@v1` and `deploy` (`pages: write`, `id-token: write`) calling `deploy.yml@v1`. `hangfolio/spike-copy-pushed` is a copy of the template's tree, pushed as a single "Initial commit" (S5 explains why it is not a generated copy). In that copy Pages was first off, then enabled through the API in branch mode (`POST /repos/{r}/pages` with `build_type=legacy`, source `main` `/`), then switched with `PUT /repos/{r}/pages -f build_type=workflow`. **Deploy site** ran in each state. A separate control workflow, `S4 control`, made the same call with less permission: one job with `contents: read` only, one with `permissions: {}` (metadata only). Runs (Node 22, `ubuntu-24.04`, `gh` preinstalled on the runner):

- Pages off: https://github.com/hangfolio/spike-copy-pushed/actions/runs/37222554542 (attempt 1) and https://github.com/hangfolio/spike-template/actions/runs/37222374668; control https://github.com/hangfolio/spike-copy-pushed/actions/runs/37222659558
- Legacy: https://github.com/hangfolio/spike-copy-pushed/actions/runs/37222701583; control https://github.com/hangfolio/spike-copy-pushed/actions/runs/37222704926
- Workflow, deployed: https://github.com/hangfolio/spike-copy-pushed/actions/runs/37222780341; control https://github.com/hangfolio/spike-copy-pushed/actions/runs/37222782372
- "Re-run all jobs" on the first run after switching to workflow: https://github.com/hangfolio/spike-copy-pushed/actions/runs/37222554542 (attempt 2)

**Result.** All three states read correctly with `pages: read`. Two details shaped the decision. First, on a public repository the call also succeeds with a metadata-only token (`permissions: {}`), so `pages: read` is not what makes it work there; it stays because configure-pages uses it and private repositories were not tested. Second, an unauthenticated request returns 404 even when Pages is on, so the token must always be passed, or every repository would look like `none`. After the switch to `workflow`, `configure-pages` reported `base_url` `https://hangfolio.github.io/spike-copy-pushed`, the deploy succeeded, and the site was served under the base path.

**Two side findings.**

1. *Re-run all jobs* re-runs the old commit. Re-running the first run (Pages had been off) after the switch gave `run_number=1 run_attempt=2`, read `build_type=workflow` and deployed. It deployed that run's commit (`b8f93c9`), however, which rolled the site back from the newest commit until the next run. The `setup-needed` message is shown on the newest run, so it is safe there. The first-run Welcome summary should instead say "click *Run workflow*" (or "re-run the newest run"), not "re-run this run".
2. Enabling branch mode first left `gh-pages` and `main` as the `github-pages` environment's custom branch policies after the switch to `workflow`. That is harmless, because `deploy` only runs from the default branch.

**Fallback.** Not needed. The planned fallback, reading the failure text of `actions/configure-pages` with `continue-on-error`, stays unused.
