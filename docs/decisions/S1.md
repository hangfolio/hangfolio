# S1: Can the theme package own Astro, every route and the content collections?

- Date: 2026-10-04
- Result: pass. The registry install and the npm-workspaces install both work. A plain `file:` symlink to a folder outside the project fails, and we will not support that layout.
- Decision: keep D1 and D2 as written, with no second `astro` dependency in the site. The theme pins `astro`, `@astrojs/mdx` and `@astrojs/markdown-satteri` exactly. It injects every page with a package-specifier entrypoint (`hangfolio/routes/...`), re-exports `collections` (glob loaders on `./content/...`), and calls `addWatchFile(site.yaml)`. It supplies MDX components through `<Content components={...}>`. Fixtures stay npm workspaces, but CI must also build one packed install (`npm pack`, then install the result into a copy of the starter), because only that layout runs the adopter's config-loading path. Markdown plugins are Sätteri plugins, not remark or rehype plugins. The `hangfolio` command sets `ASTRO_DISABLE_UPDATE_CHECK=true` before it starts Astro.

**Question.** Can a site whose `package.json` lists only the theme run `hangfolio dev` and `hangfolio build` with all pages injected by the theme and content read from `<root>/content`? Does dev reload on edits to `content/` and `site.yaml`, and does MDX at the project root resolve `astro/jsx-runtime`?

**What I tried.** I built a scratch theme (`hangfolio@0.0.0`, private, never published) on Node 22.22.3 and npm 10.9.8. It pins astro 7.3.5, @astrojs/mdx 8.0.2, @astrojs/markdown-satteri 0.4.2 and yaml 2.9.1. It ships TypeScript sources (`config.ts`, `integration.ts`, `content.ts`) plus `.astro` routes, and `bin/hangfolio.mjs` resolves `astro/package.json` from its own location and spawns that copy of the CLI.

The site uses the SPEC 4.2 plumbing:
- `astro.config.mjs` contains `export default defineSiteConfig()`;
- `src/content.config.ts` re-exports the theme's collections;
- content is `site.yaml`, `content/writing/{plain.md,x.mdx}` and `content/projects/tidepool.md`.

I installed the site in three ways:
1. **Plain symlink.** `"hangfolio": "file:../theme"` is npm's default for a folder outside the project. npm creates only the symlink and does not install the theme's dependencies. Even after running `npm install` inside the theme, the build fails: Astro's generated `astro:content` imports `astro/...` from the project root, where there is no astro.
2. **Registry-style.** I ran `npm pack` and depended on `file:../hangfolio-0.0.0.tgz`. `file:../theme` with `install-links=true` gives the same result. astro is hoisted to the site's `node_modules`, and the build exits 0.
3. **Workspaces.** The root lists `packages/theme` and `fixtures/site`, and the site depends on `file:../../packages/theme`. The build exits 0.

**Results.**
- **MDX.** `content/writing/x.mdx` compiles. `<Note>` renders with no import. `astro/jsx-runtime` resolves from `content/writing` to the hoisted copy in layouts 2 and 3.
- **Dev reload.** I drove the installed Chrome 154 with playwright-core and kept the page open while editing:
  - an edit to the MDX post showed in 124–171 ms;
  - a new post appeared on `/writing/` in about 640 ms;
  - an edit to `site.yaml` restarted the server, and the tab reloaded itself with the new name in 0.6–1.2 s.
- **Control.** With `addWatchFile` turned off, a `site.yaml` edit never appeared within 30 s, in two runs.

**Other findings that change M1:**
- **Sätteri is Astro 7's default processor.** It is the default for both Markdown and MDX. Setting `markdown.rehypePlugins` throws unless `@astrojs/markdown-remark` is installed. The base-link fix works as a Sätteri hast plugin: `markdown.processor: satteri({ hastPlugins: [...] })`, which MDX inherits. Pinned anchors (`## How it works {#architecture}`) need `features: { headingAttributes: true }`. Without it the braces render as text and the id becomes `how-it-works-architecture`.
- **Node does not strip types under `node_modules`.** It fails with `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`. So in an adopter's install, Astro loads `astro.config.mjs` through its Vite fallback, while in the workspace Node loads `config.ts` natively. Both work, but only a packed install tests the adopter's path.
- **Astro 7 backgrounds `astro dev` for AI agents.** When it detects an AI agent (the `am-i-vibing` package), it runs `astro dev` as a background server with JSON logs ("Dev server running at … Stop: astro dev stop"). `--ignore-lock` keeps it in the foreground. `hangfolio` passes its arguments through, so `hangfolio dev stop|status|logs` also work. Test harnesses must pass `--ignore-lock`.
- **The update check restarts dev.** Astro's dev update check writes `.astro/settings.json`, and the dev server restarts when that file changes. In 2 of about 15 runs this caused a restart nobody asked for: once about 1 s after "ready", which broke the requests in flight, and once 20 s into a run. The watcher log tied the first to `settings.json`. The second run was not logged, but the check is the likely cause. With `ASTRO_DISABLE_UPDATE_CHECK=true` set by the bin, 7 starts from an empty `.astro/` showed no `settings.json` events and no extra restart. The check would also suggest updating `astro` directly, which is the wrong advice when the theme pins it.
- **One entrypoint can serve several patterns.** The same entrypoint can be injected at more than one pattern; S2 uses this for redirects.
- **Upstream warning.** Rolldown's `MODULE_LEVEL_DIRECTIVE` warning about `"use astro:head-inject"` in MDX also appears in a plain Astro 7.3.5 project with no theme. It is harmless.

**Fallback.** Not needed. A second direct `astro` dependency would not fix layout 1 either, because two copies of astro would then be installed.
