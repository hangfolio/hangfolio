# S6: Reusable build and deploy workflows called from another repository

- Date: 2026-10-04
- Result: partial. Every check passed except fork pull requests, which were not run because they need a second GitHub account. Passed: cross-repository and cross-owner calls, the caller's per-job permissions, the artifact handoff, OIDC, the caller's `github-pages` environment, a same-repo pull request and a Dependabot pull request.
- Decision: Keep the plan. Every copy's `deploy.yml` stays the short caller from SPEC 8.1: `permissions: {}` at the top, `build` with `contents: read` and `pages: read`, and `deploy` with `pages: write` and `id-token: write`, calling `build.yml@v1` and `deploy.yml@v1` in the engine repository. The engine's jobs declare their own least-privilege `permissions`. The inline-workflow fallback is not adopted. One follow-up is open: a fork pull request in the canary (M-later, needs a second account).

**Question.** Can a site repository call the engine's reusable `build.yml` and `deploy.yml`, from the same owner and from a different owner, with permissions granted per job by the caller? The deploy job must use the caller's `github-pages` environment with OIDC, the Pages artifact must pass from the build workflow to the deploy workflow, and validation must pass for pull requests that get a read-only token (Dependabot, forks).

**What was tried.** `hangfolio/spike-engine` holds `build.yml` and `deploy.yml` as `workflow_call` workflows (tags `v1` = `09c6f0f`, `v2` = `df2e0a9`, a trivial change). `build.yml` has two jobs:

- `preflight` (`pages: read`) reads the Pages build type (S4) and computes `intent`.
- `build` (`contents: read`, `pages: read`) checks out the caller, sets up Node 22 with the npm cache, runs `npm ci`, runs `actions/configure-pages` when the build type is `workflow`, builds Astro 7.3.5 with `SITE_PAGES_URL`, and uploads `dist` with `actions/upload-pages-artifact` when it will deploy.

`deploy.yml` has one job (`pages: write`, `id-token: write`, `environment: github-pages`, `concurrency: pages-<repo>`). It decodes and prints the OIDC token's claims (never the token), runs `actions/deploy-pages` and smoke-checks the page. All actions are pinned by SHA: checkout v7.0.1, setup-node v7.0.0, configure-pages v6.0.0, upload-pages-artifact v5.0.0, deploy-pages v5.0.1, download-artifact v8.0.1. The callers were:

- `hangfolio/spike-copy-pushed`, the template's caller from SPEC 8.1, with Pages in GitHub Actions mode.
- A public repository under a second owner, the maintainer's personal account (`<maintainer>/hangfolio-spike-s6-caller`, Pages deliberately off). It calls only `build.yml@v1`, with an extra input that forces the artifact upload, plus a caller-owned job that downloads the artifact.
- In the same repository, a negative control that grants the build call only `contents: read`.
- In `spike-copy-pushed`, a pull request from a branch, and a Dependabot pull request drawn by deliberately pinning `actions/checkout@v4` in a side workflow.

Runs:

- Same-owner deploy: https://github.com/hangfolio/spike-copy-pushed/actions/runs/37222780341 (also 37222956413 on a push to `main`, and 37223186351)
- Cross-owner build and artifact: `https://github.com/<maintainer>/hangfolio-spike-s6-caller/actions/runs/37222445336` and `.../37223256141`
- Cross-owner negative control (startup failure): `https://github.com/<maintainer>/hangfolio-spike-s6-caller/actions/runs/37223261208`
- Pull request from a branch (https://github.com/hangfolio/spike-copy-pushed/pull/1): push run 37222895898, pull_request run https://github.com/hangfolio/spike-copy-pushed/actions/runs/37222899820
- Dependabot pull request (https://github.com/hangfolio/spike-copy-pushed/pull/2): push run 37222997126, pull_request run https://github.com/hangfolio/spike-copy-pushed/actions/runs/37223000822

**Result.**

- **Permissions.** Each called job ran with exactly what the caller's job granted, as the job logs show.
- **Negative control.** When the caller grants less than an engine job declares, GitHub refuses the whole run before any job starts. So the engine's declared permissions act as a contract that callers must meet, and validation compares them with the caller's declared permissions, not with the event's token.
- **OIDC and environment.** The OIDC token in the deploy job names the caller's repository and its `github-pages` environment, with `job_workflow_ref` pointing at the engine's `deploy.yml@refs/tags/v1`. The Deployments API of the caller lists the deployment under `github-pages`.
- **Artifact.** The artifact uploaded inside the called `build.yml` was deployed by the called `deploy.yml`. Across owners, a job in the caller downloaded it by name, with the same digest.
- **Pull requests.** Pull requests from a branch and from Dependabot ran `preflight` and `build` green with a read-only token, and `deploy` was skipped (`intent=false`). The deploy job's `pages: write` and `id-token: write` caused no validation error on the Dependabot pull request.

**Side finding.** Because the SPEC 8.1 trigger has no branch filter, a pull request from a branch in the same repository gets every check twice: once from the `push` run and once from the `pull_request` run (PR 1 and PR 2 above). That is harmless but noisy. If it matters, `push` could be limited to the default branch. Branch pushes without a pull request would then stop building, so this is a SPEC choice rather than a spike result.

**Not tested.** A fork pull request needs a second account, and forks inside this org or under the maintainer's account were out of bounds for this spike. The evidence suggests it will pass, because validation checks the caller's declared permissions (negative control) and a Dependabot pull request, which also gets a read-only token, passed. The pre-release canary should still run one fork pull request before v0.1.

**Fallback.** Not needed. The inline ~60-line `deploy.yml` with SHA-pinned actions, bumped by Dependabot's `github-actions` ecosystem, stays as the fallback if the fork pull request check fails.
