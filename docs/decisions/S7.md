# S7: Dependabot version updates in a fresh copy

- Date: 2026-10-04
- Result: partial. In a new copy pushed into an empty repository, with no setting changed, Dependabot opened the npm PR and the `github-actions` PR within a minute. It proposed `@v1` to `@v2` for a reusable-workflow ref, and each PR ran the caller's build. A copy made with "Use this template" was not generated, for the same email reason as S5 (see "Pending"). Public repositories generated from another template got their first Dependabot PR 36 to 65 seconds after creation.
- Decision: Keep the plan. The starter ships `dependabot.yml`, and the manual "Enable Dependabot" step (N701) is not needed. Change one thing in SPEC 9: the `github-actions` entry gets a `groups` rule for the engine, so that `build.yml` and `deploy.yml` move to a new major in one PR. Keep Dependabot's default 3-day cooldown. A release reaches users at the first scheduled run that is at least 3 days after it.

**Question.** Does Dependabot run version updates in a fresh template copy without any toggle? Does it propose bumps from `@v1` to `@v2` for reusable workflows? Does the PR run the caller's build?

**What was tried.**

`hangfolio/spike-copy-dependabot` is the tree of `hangfolio/spike-template` at `2b28091`, pushed as one "Initial commit" into an empty public repository. It has three changes from the template:

- `package.json` pins `kleur` at the exact outdated version `4.0.0`. The latest version is `4.1.5`, published in 2022. `kleur` stands in for the theme package.
- `dependabot.yml` is the template's file (SPEC 9: npm and `github-actions`, monthly, npm `open-pull-requests-limit: 1`, prefix "Update site theme"), with `allow` set to `kleur` only.
- `deploy.yml` is unchanged. It calls `hangfolio/spike-engine` `build.yml@v1` and `deploy.yml@v1`, and `v2` exists there.

The first Dependabot log in `spike-copy-pushed` showed a cooldown, so the copy also has `s7-aged-engine.yml`. It is the same caller, pointed at `hangfolio/spike-engine-aged`. That repository holds the same two workflows, with tags `v1` and `v2` on commits whose dates were set in the past on purpose (2026-09-01 and 2026-09-15). That makes `v2` look older than the cooldown.

No repository or organization setting was changed, and GitHub Pages stayed off. Step 2 then pushed a `groups` rule for the engine into `dependabot.yml` (commit `666dab3`), which is a config change and not a setting.

**Result.**

- **Without any toggle.** Version updates ran on the first push. The org defaults for new repositories are all off, Dependabot security updates are off, and the dependency graph API returns 404. A `dependabot.yml` on the default branch is all that version updates need. The jobs show up as "Dependabot Updates" runs (event `dynamic`) in the repository's Actions list. That list is the API-visible form of Insights → Dependency graph → Dependabot, which has no REST endpoint of its own.
- **Timing.** The repository was created at 18:17:06Z and the push came about 4 seconds later. Both Dependabot jobs were queued at 18:17:18Z, and the three PRs opened at 18:17:50Z, 18:17:51Z and 18:18:08Z. The schedule (`monthly`) only governs later runs. The first run happens when the config lands on the default branch.
- **npm.** "Update site theme: Bump kleur from 4.0.0 to 4.1.5" changes the exact pin in `package.json` and the lockfile entry. When Dependabot ran again after step 2, it logged "Pull request #3 already exists" and opened nothing new.
- **`@v1` to `@v2` for reusable workflows.** Dependabot does propose it, and it keeps the major-only form (`@v1` becomes `@v2`, never `@v2.0.0`). Each `uses:` line is a separate dependency, named `<owner>/<repo>/.github/workflows/<file>`. Without a group rule, the engine's two refs came as two PRs. Merging only one of them would run `build.yml@v2` with `deploy.yml@v1`. With `groups: { engine: { patterns: ["hangfolio/spike-engine-aged/*"] } }`, both refs came as one PR (#4), and Dependabot closed #1 and #2 with "Superseded by #4."
- **Cooldown.** For `hangfolio/spike-engine`, whose `v2` tag was pushed the same day, Dependabot logged "Available release version/ref is 2", then "Days since release : 0 (cooldown days 3)", and proposed nothing. The 3 days are dependabot-core's default when `dependabot.yml` sets no `cooldown` (`DEFAULT_COOLDOWN_DAYS = 3` in `updater/lib/dependabot/job.rb`). For npm, it passes `--min-release-age=3` to `npm install`. For git tags, the release date comes first from a GitHub Release's `published_at`, then from the tag's creation date, and last from the commit date (`common/lib/dependabot/git_cooldown_date_resolver.rb`).
- **The PR runs the caller's build.** Every Dependabot PR triggered both caller workflows twice: once on `push` to the `dependabot/...` branch and once on `pull_request`. All of them were green, ran with a read-only token, and skipped `deploy`. The pull_request runs used the proposed version (`build.yml@refs/tags/v2`, "engine v2"). PR #3 installed the bumped lockfile. Each PR therefore shows every check twice, which is the side finding from S6.

**Decision for SPEC 9.**

1. `dependabot.yml` in the starter gets a group rule, so an engine major arrives as one PR that moves both refs. The pattern matches the reusable-workflow dependency names:

   ```yaml
     - package-ecosystem: github-actions
       directory: /
       schedule: { interval: monthly }
       groups:
         engine:
           patterns: ["hangfolio/hangfolio/*"]
   ```

   A `commit-message` prefix such as "Update site engine" would make the PR title friendlier than "Bump the engine group with 2 updates". That is optional.

2. No `cooldown` key. Waiting 3 days protects users from a bad release. Because the schedule is monthly, a theme release or engine major normally reaches users at the next monthly run. The SPEC's "Dependabot opens 'Update site theme to 1.4.0'" timing should say that.
3. The engine publishes a GitHub Release for each major tag. Dependabot then counts the cooldown from the release, not from a commit that may be older.

**Pending.** A copy actually generated with "Use this template" (`POST /repos/hangfolio/spike-template/generate`) was not made, for the same reason as in S5. The generated repository's initial commit would carry the maintainer's web commit email, which must not appear in project repositories. Once the owner turns on *Keep my email addresses private* (or accepts that email in a throwaway repository), generate a copy from `spike-template` unchanged after 2026-10-07 18:00 UTC. By then `spike-engine`'s `v2` is out of cooldown, so the copy should get its `@v1` to `@v2` PRs within about a minute. Record the times here. The ten generated repositories above already point to "yes".

**Fallback.** Not needed so far. If the generated copy gets no PR, adopt the documented manual step: Insights → Dependency graph → Dependabot → "Check for updates", or any edit to `dependabot.yml`, with notice N701 pointing to it.
