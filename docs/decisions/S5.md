# S5: The first run of a new copy

- Date: 2026-10-04
- Result: partial. The push behaviour of a new repository's first commit was measured. The template generation itself ("Use this template", `POST /repos/{template}/generate`) was not run yet; see "Pending".
- Decision: The welcome logic treats `github.run_number == 1` as the first run, as the fallback in the plan says. `github.event.created` is not used: it is `true` for every push that creates a branch, so it adds nothing that `run_number` does not already give. A re-run of run 1 keeps `run_number == 1` (with `run_attempt == 2`), so it still counts as the first run. That is the behaviour the Welcome summary wants.

**Question.** Does the initial commit of a template copy fire `push`, and what are `github.event.created` and `github.run_number` on that run?

**What was tried.** `hangfolio/spike-template` (`is_template: true`) has a **Deploy site** workflow whose first job, `First-run facts (S5)`, runs with `permissions: {}`. It prints `github.event_name`, `github.event.created`, `github.run_number`, `github.run_attempt`, `github.ref` and selected fields of `$GITHUB_EVENT_PATH` (`created`, `before`, `forced`, the number of commits). Two repositories received their first commit by a push into an empty repository: the template itself (https://github.com/hangfolio/spike-template/actions/runs/37222374668) and `hangfolio/spike-copy-pushed`, whose single "Initial commit" has the template's exact tree (https://github.com/hangfolio/spike-copy-pushed/actions/runs/37222554542). Later runs in the copy covered a second push to `main`, a push of a new branch, a Dependabot branch, `workflow_dispatch` and a re-run. To check that template generation fires `push` at all, the public run history of three repositories generated in 2026 from a widely used public template (`JetBrains/intellij-platform-plugin-template`, which ships push-triggered workflows) was read through the API. Only metadata was read; those repositories are not named here.

**Result.** The first push fires `push` with `event.created=true`, `before` all zeros and `run_number=1`. In the generated repositories, each workflow's run 1 is a `push` run on "Initial commit", queued 7 to 10 seconds after the repository was created. So template generation fires `push` too. Whether `event.created` is `true` on that generated commit is still unmeasured, and the decision does not depend on it.

`run_number` counts per workflow file, so the rule holds as long as `deploy.yml` keeps its path. It is plumbing that never moves within a major (SPEC section 9).

**Pending.** Generating `hangfolio/spike-copy-a` from the template was skipped on purpose. A generated repository's initial commit is authored with the generating account's web commit email. The maintainer's current web commit email is a personal address that must not appear in project repositories. The fix needs the owner, not code: either turn on *Keep my email addresses private* in GitHub's email settings (web-based Git operations then use the `users.noreply.github.com` address), or explicitly accept that email in a throwaway repository. After either one, generate the copy and add `event.created` and `run_number` from its first run here.

**Fallback.** `run_number == 1` alone. It is now the decision, so nothing else depends on the pending check.

## Generated copy

- Date: 2026-10-04
- Result: pass. A copy made with the generate API fires `push` on its "Initial commit" with `event.created=true` and `run_number=1`, the same values as a first push into an empty repository. With *Keep my email addresses private* on, that commit carries only the account's GitHub no-reply address and no denylist term.
- Decision: unchanged. `run_number == 1` stays the first-run test. The "Pending" item above is done, and the email reason no longer blocks generated copies (S3, S7).

**What was done.** After the owner turned on *Keep my email addresses private*, `hangfolio/spike-email-check` was generated from `hangfolio/spike-template` at `2b28091` (`POST /repos/hangfolio/spike-template/generate` with `private: true` and `include_all_branches: false`). `spike-template` and `spike-engine` were unarchived for the run and archived again afterwards. The copy has a single commit whose tree is the template's exact tree (`f9572b9`). Its author is the generating account's profile name with that account's `<id>+<login>@users.noreply.github.com` address. Its committer is `GitHub <noreply@github.com>` (login `web-flow`), and the signature is verified. The commit metadata, the 12 file paths and the contents of every file were scanned with the same case-insensitive fixed-string match that `.githooks/pre-push` uses, and no denylist term matched. The copy's **Deploy site** run 1 was queued 11 seconds after the repository was created and printed the same first-run facts as the pushed copy. `deploy` was skipped because Pages is off (`build_type=none`, as in S4). The copy was then archived and left private.
